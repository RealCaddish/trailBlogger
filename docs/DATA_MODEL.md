# Data model (v2)

Two GeoJSON FeatureCollections, both with `"schema": "trailblogger/v2"`.

## `data/hikes.geojson`

One feature per hike. Full-resolution `LineString`, coordinates rounded to
six decimals, with elevation as a third value when the GPS had it.

| property | type | notes |
|---|---|---|
| `id` | string | 12 hex chars, never changes; also the photo folder name for new hikes |
| `name` | string | |
| `date` | `YYYY-MM-DD` or null | |
| `length_mi` | number | computed from the track |
| `elevation_gain_ft` | number or null | cumulative ascent with a 3 m hysteresis filter |
| `country`, `state`, `park`, `park_type` | string or null | computed by point-in-polygon at import time |
| `journal` | string | light Markdown |
| `photos` | array | `{ src, taken?, lat?, lon?, located_by? }`, `src` is relative to `data/trail_images/`; `lat`/`lon` come from EXIF GPS, or from the track by time (`located_by: "time"`) when the track has `times` |
| `weather` | object or null | `{ code, tmax, tmin, precip_in, wind_mph, source }` for the hike date, from Open-Meteo; `code` is a WMO weather code |
| `start_time`, `times` | ISO datetime, array of ints | only for recorded or timed GPX tracks: seconds since `start_time` for each coordinate |
| `companions` | array of strings | |
| `tags` | array of strings | reserved |
| `osm_ids` | array of strings | OpenStreetMap ways this hike covers (removed from the wishlist) |
| `legacy_id` | number or null | the old `trail_id`; explains folder names like `trail-1761587899908` |
| `created_at`, `updated_at` | ISO datetime | |

The same trail hiked twice is two features (for example the two Graenidalur
Loop entries).

## `data/wishlist.geojson`

One feature per trail to do. Geometry is simplified (about 8 m tolerance),
2D, five decimals. It is a `LineString`, or a `MultiLineString` when the
trail is an OpenStreetMap relation whose pieces do not connect end to end
(joining them would draw straight lines across the map).

| property | type | notes |
|---|---|---|
| `id` | string | derived from the OSM id, so re-imports are idempotent |
| `name`, `length_mi`, `country`, `state`, `park`, `park_type` | | as above |
| `note` | string | why you want to do it, when, with whom |
| `source` | `OpenStreetMap` or `user` | |
| `osm_id` | string or null | |
| `osm_ids` | array | other OSM ways merged into this one |
| `created_at` | ISO datetime | |

## De-duplication rules

Applied by `scripts/migrate_v2.py` and `scripts/import_osm.py`, using
`geo.py`:

- A wishlist trail is dropped as *already hiked* when 90% of its vertices lie
  within 40 m of a hike track. Its OSM id is added to that hike's `osm_ids`.
- Two wishlist trails are the same route when each lies 95% within the
  other, or when their names match ignoring accents and one is contained in
  the other. The longer geometry is kept, with the accented spelling.
- Renamed copies of a hike (identical geometry) are merged.

## Derived files

- `data/parks_visited.geojson`: park polygons that contain at least one hike,
  simplified. Regenerated by the migration script; the editor does not update
  it, so re-run the script (or delete the file) when you hike in a new park.
- `data/backups/`: rolling copies written by `server.py`, ignored by git.
